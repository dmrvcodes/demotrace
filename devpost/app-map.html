A take-home guide to the code. Snapshot of commit 07bd8e7 (25 October 2026); the code can drift after this, so trust the source over this page.

What it is, in one paragraph

You upload a demo video (up to 3 minutes) and 3–5 claims. A Worker on AWS Lambda takes frames and a transcript, asks Claude one structured question per claim — Shown, Told only or Missing, and which frames or speech segments prove it — then checks that every cited piece of evidence really exists and computes the timestamps itself. The browser shows the video next to one card per claim; a click on a timestamp jumps to that second. The video is deleted from S3 right after download.

One action through the code: "analyze my video"

Outlined in green: the two places that carry the product's core idea — telling "said" apart from "shown".

A three-stop route (reference route)

1

web/src/app/page.tsx — search runLiveAnalysis.

The whole browser side of an analysis in one function: create the job, upload the file with the presigned POST, start the analysis with the claims, then poll until it is completed or failed. The video you play is your local file, never one downloaded back.

2

backend/worker/demotrace/handler.py — search def handler and tracker.stage(.

The Worker claims the job only if it is still queued, then runs named stages. A failure is recorded with its stage and a specific code, so a failed job says what actually broke. The video is deleted from S3 right after the download.

3

backend/worker/demotrace/validate.py — search assemble_result.

Where the model's answer is checked against this job's own frames and speech: unknown IDs, a Shown claim without a frame, Missing with evidence — all rejected. Timestamps come from our frames, not from the model. The rule that a promise slide is never Shown lives in the prompt (SYSTEM_PROMPT in llm/prompt.py) and is measured by the eval.

A practice to reuse

Write the observable result down first, then score the system against it. The PRD said a slide that promises a feature is never Shown. That became hand-labelled negative cases — including a hovered button, a screenshot embedded in a slide, a partial create-and-share claim and a silent caption — and a scorer, eval/score.py, that reports any false Shown separately. The 25 October live run scored 27/27 statuses, 100% evidence hits and 0/16 false Shown across six recordings; eval/run.py --min-cases 6 refuses to claim this gate from fewer than six cases.

On another project: turn the one rule your product must never break into a labelled example with a negative case, before you tune anything, so "it looks right" becomes a number you can rerun.

Run it again

Try the live app

Open demotrace.vercel.app, click Try with sample, click a timestamp. For a live analysis, drop your own MP4 (up to 3 minutes, English narration) and enter 3–5 claims.

Interface locally, no cloud

cd web && npm ci && npm run dev, then open http://localhost:3000 and use the sample.

Pipeline and tests locally

.venv/bin/python -m demotrace.cli prepare VIDEO --out out/x — frames and transcript only, no model call.

PYTHONPATH=backend/worker:backend/shared:backend/control .venv/bin/pytest -q backend/worker/tests backend/control/tests eval/tests

.venv/bin/python eval/run.py — the quality gate over recorded runs.
